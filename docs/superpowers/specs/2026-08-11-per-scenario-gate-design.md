# Ворота етапу 2: окрема зелена зона на кожен сценарій

Дата: 2026-08-11

## Проблема

Умова c3 у `web/src/engine/gate.ts` вимагає ≥80% лише від тих сценаріїв, у яких
у спільному вікні 150 рук набралось ≥15 рук:

```ts
const scen = [...aggregate<Scenario>(w, 's')].filter(([, d]) => d.t >= GATE.scenMin)
const c3 = w.length >= GATE.hands && scen.length > 0 && scen.every((s) => s.p >= GATE.acc)
```

За замовчуванням активний лише сценарій `rfi` (`store/sessionStore.ts:46`), і
перемикачі сценаріїв нічого не зобов'язують. Тому етап 2 сьогодні відкривається
одним сценарієм: решта три просто не потрапляють у розрахунок. «Проти 3-бету»
можна не бачити жодного разу — ворота цього не помітять.

Потрібно, щоб усі чотири сценарії — Відкриття, Проти лімперів, Проти рейзу,
Проти 3-бету — були в зеленій зоні **окремо**, а не в сумі.

## Рішення

Кожен сценарій рахується у **власному ковзному вікні**: останні 40 записів саме
цього сценарію в журналі, незалежно від того, що відбувалось між ними.

```
c3 = усі 4 сценарії мають ≥40 рук у своєму вікні І ≥80% на цих 40
```

Сценарій, у який гравець не грав, більше не «не рахується» — він показує `0 / 40`
і тримає ворота закритими.

### Чому окремі вікна, а не спільне

Розглядались три варіанти: спільне вікно 150, спільне вікно 300–400, окреме вікно
на сценарій. Обрано окремі вікна.

При спільному вікні блокове тренування себе з'їдає: гравець бачить провал у
«Проти 3-бету», грає 150 рук цього сценарію — і три інші випадають з вікна, тож
ворота знову закриті, хоча він щойно підтягнув найслабше місце. Окреме вікно
зберігає форму по кожному сценарію незалежно: «Відкриття» пам'ятає свої останні
40 рук, навіть якщо вони були вчора.

На мультирежим вибір не впливає: сценарій кожної відповіді пишеться в журнал
(`engine/progress.ts:165`), і зріз завжди береться фільтром по цьому полю.
З усіма чотирма увімкненими сценарій вибирається рівномірно (`engine/spots.ts:217`),
тож ~160 рук міксом наповнюють усі чотири вікна одночасно.

### Чому 40

На 40 руках 8 помилок — це рівно 80%: одна зайва помилка вибиває з зеленого.
Менша дистанція (30) дозволяє впіймати зелену зону вдалою серією; більша (60)
відсуває етап 2 на 240 рук мінімуму і довше тримає стару просадку у вікні.

## Зміни

### 1. `web/src/engine/gate.ts`

Константи:

| Ключ | Було | Стало | Роль |
|---|---|---|---|
| `hands` | 100 | **160** | c1 — загальний лік рук. 4 × 40 і є реальний мінімум етапу |
| `scenMin` | 15 | — | зникає |
| `scenWindow` | — | **40** | вікно на сценарій |
| `winMin` | — | **100** | скільки рук має бути у спільному вікні, щоб c2 і c4 рахувались |
| `window` | 150 | 150 | спільне вікно для c2 і c4 |
| `acc` | 80 | 80 | поріг зеленої зони |
| `posMin`, `posCount` | 8, 8 | без змін | |

`winMin` окремою константою — обов'язково. Сьогодні `c2` і `c4` мають охоронця
`w.length >= GATE.hands`, де `hands` грає дві ролі одразу: загальний лік і
мінімальне заповнення вікна. Якщо просто підняти `hands` до 160 при вікні 150,
охоронець `w.length >= 160` не спрацює ніколи і ворота зачиняться назавжди.

Тип зрізу сценарію отримує явний вердикт:

```ts
export interface ScenStat extends SliceStat<Scenario> {
  readonly ok: boolean
}
```

`GateStatus.scen` змінює контракт: замість відфільтрованого списку — **завжди
рівно 4 елементи** у порядку `SCENARIO_KEYS` (rfi, iso, vsraise, vs3bet).
Сценарій без жодної руки присутній зі значеннями `t: 0, p: 0, ok: false`.

Розрахунок:

```ts
const scen: ScenStat[] = SCENARIO_KEYS.map((k) => {
  const sw = recent.filter((e) => e.s === k).slice(-GATE.scenWindow)
  const p = sw.length ? (sw.filter((e) => e.ok).length / sw.length) * 100 : 0
  return { k, p, t: sw.length, ok: sw.length >= GATE.scenWindow && p >= GATE.acc }
})
const c3 = scen.every((s) => s.ok)
```

Вхід — увесь `recent` (до 400 записів), а не зріз останніх 150: у цьому й сенс
незалежного вікна. `c3` більше не має охоронця по спільному вікну — його роль
виконує вимога `t >= scenWindow` у кожному сценарії.

`c1`, `c2`, `c4` лишаються як є, з заміною `GATE.hands` на `GATE.winMin` в
охоронцях `c2` і `c4`. Позиції (c4) свідомо не чіпаються: вони рахуються по
спільному вікну 150, як і зараз.

### 2. `web/src/components/GateLock.tsx`

Умов лишається чотири — інакше довелось би переписувати «за всіма чотирма
умовами» у текстах воріт (`pages/Train.tsx:51`) і лічильник у `App.tsx:36`.
Третя умова отримує під собою смужку з чотирьох плиток.

- `Criterion` отримує необов'язковий `children?: React.ReactNode`, який
  рендериться під `.d` і над `.pbar`.
- Заголовок c3: `Кожен із 4 сценаріїв ≥ 80%`.
- Значення c3: `готово N з 4`, де N — `g.scen.filter((s) => s.ok).length`.
- Прогрес c3: `(N / 4) * 100`.
- Опис c3: пояснює, що кожен сценарій рахується по своїх останніх 40 руках
  незалежно від інших, тож слабкий режим можна добивати окремо.
- Всередину c3 — наявний `PerPos` (`components/StatStrip.tsx:21`), який уже
  реалізує рівно цю зелену зону на порозі 80%:

```tsx
<PerPos
  items={g.scen.map((s) => ({
    name: SCENARIOS[s.k].label,
    acc: s.t ? Math.round(s.p) : null,
    t: s.t,
    min: GATE.scenWindow,
  }))}
/>
```

Назви беруться повні (`label`: «Відкриття», «Проти лімперів», «Проти рейзу»,
«Проти 3-бету»), а не `short`. Плитка — `minmax(100px, 1fr)` з mono 10.5px
(`styles/app.css:838`); найдовше «Проти лімперів» переноситься по пробілу на два
рядки і вміщується. Екран воріт пояснювальний, скорочення тут гірші за перенос.

Змінна `worstScen` та її сортування зникають — вони існували, щоб показати
найгірший сценарій одним рядком.

### 3. `web/src/api/serverProgress.ts`

```ts
supabase.rpc('recent_attempts', { window_size: GATE.window })   // 150
```
→
```ts
supabase.rpc('recent_attempts', { window_size: RECENT_LIMIT })  // 400
```

Для чотирьох вікон по 40 рядків 150 замало: при блоковому тренуванні релевантні
руки розкидані далі по журналу. `RECENT_LIMIT` (`engine/progress.ts:61`) — рівно
стільки ж, скільки тримає localStorage, тож серверні й локальні ворота рахуються
з ідентичного входу. SQL ріже вхід на 1000
(`supabase/migrations/20260810150100_stats.sql:57`), міграція не потрібна.

### 4. `web/src/pages/Stats.tsx`

Плитки сценаріїв за весь час підписані `поріг {GATE.acc}% при {GATE.scenMin}+ руках`
і передають `min: GATE.scenMin`. Після видалення `scenMin` обидва місця беруть
`GATE.scenWindow` (40). Текст стає «поріг 80% при 40+ руках».

`pages/Review.tsx` тримається на `GATE.posMin` — не змінюється.

## Хто вже відкрив етап 2

Не постраждає. `postUnlocked` зберігається і свідомо ніколи не відкликається
(`store/progressStore.ts:86`): ворота існують, щоб дійти до постфлопу
підготовленим, а не щоб карати за просадку. Суворіші умови діють лише на тих,
хто їх ще не пройшов.

## Тести

`web/src/engine/gate.test.ts` — два наявні тести на c3 (рядки 65 і 79) описують
старе правило «сценарій із менш ніж 15 руками не рахується» і замінюються.

Хелпер `passingWindow()` дає 8 позицій × 15 рук = 120 записів, тобто по 30 на
сценарій — цього замало і для c3 (треба 40), і для c1 (треба 160). Довести до
**8 позицій × 20 рук = 160 записів**: сценарії так само чергуються через `i % 4`,
тож кожен отримує 8 × 5 = 40 рук, а `total: 160` задовольняє c1.

Наслідок, який ламає наявний тест: 160 записів більші за спільне вікно 150, тож
перші 10 записів (це UTG) у нього не потрапляють. Тест «c4: слабка позиція
блокує» (рядок 103) псує `w[0..14]` в розрахунку, що це і є UTG всередині вікна —
після зміни псувати треба записи, які реально лишились у вікні.

Нові випадки:

1. Усі 4 сценарії по 40 рук на 100% → `c3 === true`.
2. Три сценарії по 40, четвертий 39 рук → `c3 === false` (недобрана дистанція).
3. Сценарій відсутній у журналі повністю → `c3 === false`, у `g.scen` він
   присутній з `t: 0`.
4. `g.scen` завжди має довжину 4 і порядок `SCENARIO_KEYS` — навіть на порожньому
   журналі.
5. 79% на останніх 40 руках сценарію → `false`; 80% → `true`.
6. **Незалежність вікон:** 40 бездоганних рук `vs3bet`, після них 300 рук `rfi` —
   `vs3bet` лишається зеленим, хоча далеко за межами спільного вікна 150.
7. Давні помилки за межами останніх 40 рук сценарію не тягнуть його вниз.
8. `c1` перемикається на 160 (`GATE.hands - 1` → false, `GATE.hands` → true).
9. Охоронець `winMin`: спільне вікно з 99 рук лишає `c2` і `c4` закритими.

`web/src/components/GateLock.test.tsx` — новий, у стилі наявного
`components/DrillBar.test.tsx`: на порожньому прогресі рендеряться рівно чотири
плитки сценаріїв із повними назвами, сценарій без жодної руки показує «—», а
значення умови c3 читається як «готово 0 з 4».

## Поза межами

- Позиції (c4) — окремі вікна для них не робляться.
- Поріг 80% не змінюється в жодному місці.
- Перемикачі сценаріїв на екрані тренування не отримують індикації «цей режим ще
  не зелений». Може бути окремою зміною.
