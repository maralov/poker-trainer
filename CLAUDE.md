## Що це

Тренажер префлопу 9-max кешу. `poker-trainer.html` у корені — **джерело істини
для ігрової логіки**: діапазони, побудова спотів і критерії воріт перенесені з нього
1:1 і звіряються з ним тестами. Нічого не «покращувати» на ходу — якщо здається,
що діапазон неправильний, це окреме продуктове рішення, а не частина міграції.

Етап 2 (постфлоп) живе в `web/src/engine/postflop/`. Джерела істини тут два:
флоп-ядро лінії агресора (`evaluate`, `texture`, матриця «можу ставити»)
перенесене з `poker-trainer.html` 1:1 і звіряється з ним фікстурою
`__fixtures__/ref-postflop.json`; терн, рівер, захист і профіль опонента
референсу не мають — їх задає
`docs/superpowers/specs/2026-08-11-postflop-stage-design.md`. Міняти числа
профілю чи клітинки матриць можна лише разом зі спекою.

## Архітектура

```
web/        React 19 + Vite + TS (strict) — увесь застосунок
supabase/   Postgres: міграції, RLS, SQL-функції, інтеграційні тести
```

Свого бекенду немає. Supabase дає Postgres, Google-логін і RLS; клієнт пише
події напряму, ізоляцію користувачів забезпечують політики.

**Чому не свій бекенд.** Застосунку треба рівно три речі: хто цей користувач,
надійний журнал подій, агрегації над ним. Ні фонових задач, ні інтеграцій,
ні складної авторизації. Свій сервер тут додав би другий деплой, свою auth
(відновлення пароля, підтвердження пошти, refresh-токени, rate-limit) і нічого
не дав би натомість.

## Архітектурні правила

1. **Сирі події, не агрегати.** Кожна відповідь — окремий рядок у `attempts`.
   Жодних лічильників у базі. Побачив колонку-лічильник — це помилка.

2. **Журнал незмінний.** У таблиці немає політик UPDATE і DELETE: переписати
   історію не може навіть її власник. `service_role` (ключ, який ніколи не
   потрапляє в браузер) виняток — для обслуговування.

3. **RLS — це вся безпека.** Anon-ключ публічний і лежить у бандлі; єдине, що
   не дає прочитати чужий журнал, — політики. Тому вони покриті тестами
   (`supabase/tests/rls.test.ts`), і будь-яка зміна схеми має проходити їх.
   **GRANT і RLS — різні механізми, потрібні обидва**: без табличних привілеїв
   PostgREST відповідає «permission denied» ще до перевірки політик.

4. **Логіка живе в TS, SQL лише рахує.** Ворота, drill-пул і діагностика
   написані в `web/src/engine/` і покриті тестами. SQL-функції роблять тільки
   `GROUP BY` і віддають зрізи сирих подій; серверний прогрес збирається у ту саму
   структуру `PreProgress` (`api/serverProgress.ts`), тож Stats, Review і ворота
   працюють однаковим кодом і для локальних, і для серверних даних.
   Продублювати діагностику в SQL — заборонено: два джерела істини розійдуться.

5. **`engine/` не імпортує нічого зовнішнього.** Ні React, ні zustand, ні DOM,
   ні supabase. Це умова того, що логіку можна тестувати без рендера і без мережі.

6. **Тренування не залежить від мережі й логіну.** Кожна відповідь спершу лягає
   в чергу в localStorage і лише потім їде батчами. Немає мережі, немає логіну,
   сервер віддав помилку — черга накопичується, тренування працює.

7. **Ідемпотентність синку.** Кожна подія несе `client_id`; у базі стоїть
   `unique (user_id, client_id)`. «Надіслати ще раз» — завжди безпечно.

## Стиль

- **TypeScript:** `strict`, без `any`. Незнайомий тип — `unknown` плюс звуження.
- **SQL:** міграції тільки через `npm run db:new`, ніяких змін через Studio.
  Після зміни схеми — `npm run db:types`.
- **Коментарі українською — норма.** Назви змінних, функцій, файлів, колонок —
  англійською. Коментар пояснює *чому*, а не *що*.
- **Секрети тільки з env.** `.env.example` тримати актуальним.
  `service_role`-ключ не має потрапляти в жодну змінну з префіксом `VITE_`:
  усе з цим префіксом Vite вшиває в публічний бандл.
- **Коміти:** `phase-N: короткий опис`.
- Не додавати залежність, якщо задача вирішується стандартною бібліотекою.

## Узгоджені відхилення

| Було в PLAN.md | Стало | Чому |
|---|---|---|
| FastAPI + SQLAlchemy + власна auth | Supabase, без бекенду | Обґрунтуванням власної auth була навчальна цінність; проект продакшн-орієнтований |
| bcrypt + JWT, email+пароль | Google OAuth | Немає паролів — немає відновлення, підтвердження пошти й витоків |
| `attempts.raiser_pos` | `villain_pos` + `limpers` | Для `vs3bet` контекст — 3-бетор, для `iso` — кількість лімперів; без цього drill не відтворює спот |
| колонка `position` | `hero_pos` | `position` — зарезервоване слово SQL, не проходить у `returns table` |
| `GET /stats/*` з готовими агрегатами | SQL віддає зрізи, рахує engine | Інакше логіка воріт існувала б двічі — у TS і в SQL |
| React 18 | React 19 | Дає `npm create vite`; підстав фіксувати 18 немає |
| Стилі на розсуд | Звичайний CSS 1:1 з референсу | Переписування під utility-класи означало б дрейф вигляду |

Нове відхилення — вписувати сюди рядок з причиною.

## Що переноситься зі старої версії, а що ні

Standalone-версія зберігала повний запис (рука, позиція, вибір) **лише для
помилок**; правильні відповіді лягали в лічильники без деталей, а `recent` не
містить руки — а вона в базі обовʼязкова. Тому на сервер переносяться тільки
помилки. Вигадати руку заради красивого `total` означало б зіпсувати всю
подальшу статистику.

## Пастки цього оточення

- У zsh користувача `cp` — аліас на `cursor`. Використовуй `/bin/cp`, інакше
  замість копіювання відкриється редактор, а команда поверне 0.
- Паралельні Bash-виклики ділять один шелл: `cd` з одного впливає на інший.
  Використовуй абсолютні шляхи.
